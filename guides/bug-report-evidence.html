How to write a bug report that another tester can reproduce

A useful bug report is not a diary entry. It is a compact evidence package that lets another person reproduce the problem, judge impact and decide what to do next.

Use this six-part report structure

  1. Title: behavior + context + result.
  2. Environment: browser/device/build/account state when relevant.
  3. Preconditions: the state needed before step 1.
  4. Steps: the minimum sequence that reproduces the problem.
  5. Expected vs actual: separate the requirement from the observed behavior.
  6. Evidence + impact: screenshot/video/log reference plus why the issue matters.

Weak vs stronger example

Weak

Checkout broken. Button did nothing.

Missing context, setup, exact steps, expected behavior and evidence.

Stronger

Chrome 153 · Cart with 1 item · Pay now leaves checkout unchanged after valid form submission.

Then list exact steps, expected navigation, observed result, timestamp and screenshot.

Evidence checklist

  • Can a teammate reproduce it without asking you a question first?
  • Did you capture only relevant evidence, not unrelated private data?
  • Does the title identify the user action and failure?
  • Are expected and actual results written separately?
  • Did you record environment and state that could change the outcome?
  • Did you avoid guessing the root cause without evidence?
